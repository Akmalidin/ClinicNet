# Фаза 5, под-модуль 2 — AI-триаж: разведка и решения

Управляющий документ поверх `ClinicNetPhase5StarterPrompt.md`, тем же
форматом, что `docs/PHASE2-REFERRALS-DESIGN.md` — что нашли, что решили и
почему, до того как это разошлось по коду.

## Разведка

- **`available_slots`** (`apps.referrals.views.ReferralViewSet.available_slots`,
  Фаза 2) подтверждён как переиспользуемый: считает свободные окна одного
  врача на дату из `StaffBranchAssignment` минус занятые `Appointment`.
  Принимает конкретного `doctor`, не специальность — обёртка
  `triage_service.django_client.DjangoClient.find_nearest_slot` сама
  перебирает врачей нужной специальности (`GET /doctors/?specialty=`,
  уже существовавший фильтр) и берёт ближайший слот среди них.
- **Read-replica не существует.** `docs/DEPLOY.md` подтверждает: один VPS,
  один общий кластер Postgres, обслуживающий ещё 3 чужих продукта. Поднять
  реальную стриминг-репликацию — отдельная, более рискованная
  инфраструктурная задача, вне рамок этого под-модуля.
- **Ни Telegram/WhatsApp-токена, ни отдельного LLM API-ключа в проекте не
  было** — оба уточнены у пользователя явно перед стартом (см. чат).

## Решения (согласованы с пользователем перед реализацией)

1. **Канал: только Telegram на первом шаге.** WhatsApp Business API требует
   одобрения Meta и бизнес-аккаунта — Telegram Bot API получается за минуты
   через BotFather. Архитектура (`bot.py`/`telegram_client.py`) не завязана
   на Telegram настолько, чтобы WhatsApp потребовал переписывать оркестрацию
   — только новый транспортный клиент.
2. **Read-replica: сервис читает через Django REST API напрямую**, не через
   отдельное подключение к Postgres (и тем более не к несуществующей
   реплике). `DjangoClient` — единственная точка входа в данные ClinicNet;
   Django остаётся единственным местом, которое знает схему
   мультитенантности и RBAC, так же, как для любого другого клиента API.
   Нагрузка на транзакционную БД от AI-триажа — ровно то же самое, что уже
   создаёт браузер координатора, кликающий по `available_slots` вручную;
   отдельного read-нагруженного пути к БД в обход Django не появилось.
3. **LLM — опционален, не жёсткая зависимость.** `classifier.py` определяет
   `KeywordSpecialtyClassifier` (по умолчанию, без внешних зависимостей) и
   `AnthropicSpecialtyClassifier` (включается сам, как только задан
   `ANTHROPIC_API_KEY`, без других изменений кода). Тот же принцип, что уже
   применён в проекте к Celery/CRM — не поднимать то, что пока не доказало
   ценность, если без этого можно обойтись рабочим упрощением.
4. **Координатор только подтверждает.** `TriageSuggestion` — предложение,
   не бронь; `confirm()` требует явного `patient` от координатора (никакого
   silent auto-linking по телефону из чата — телефон, который человек
   печатает в Telegram, недостаточно надёжен для тихой привязки к
   медицинской карте). Реальный `Appointment` создаётся только в момент
   подтверждения, и заново проходит проверку `Appointment.clean()` на
   пересечение (слот мог быть занят кем-то другим между предложением и
   подтверждением).

## RBAC

`triage.view`/`triage.manage` — branch-scoped, `receptionist`/`branch-admin`
(та же роль "координатора", что уже даёт `churn.view`/`churn.manage`).
`triage.ingest` — отдельный код, только у нового системного аккаунта роли
`triage-bot` (`branch_scope=ALL`, бот не привязан к одному филиалу — вносит
предложение в тот филиал, где нашёлся ближайший слот). Врачу не выдано ни
одного из трёх — та же логика, что применена к churn.*.

## Известный пробел, найденный вживую

`available_slots` (сам Django-эндпоинт Фазы 2, не новый код) вычисляет окна
дня чисто по расписанию смены — без понятия "сейчас". Запрос на СЕГОДНЯ
после конца/середины смены возвращает уже прошедшие окна как «свободные».
Пойман не юнит-тестом, а живой проверкой (сессия шла позже реального начала
смены врача) — `find_nearest_slot` теперь сам отфильтровывает слоты раньше
текущего момента, не трогая сам эндпоинт (другие вызывающие стороны — UI
направлений — полагаются на его сегодняшнее поведение).

## Ограничение среды разработки

Egress-политика песочницы, где вёлся код, блокирует `api.telegram.org`
(организационная политика, не временный сбой). Проверено вживую: весь
путь classify → find_nearest_slot → ingest → подтверждение координатором →
реальный `Appointment` — против реально запущенного Django-сервера, с
заменённым только Telegram-транспортом (`FakeTelegramClient` в тестовом
скрипте). Буквальная связь с Telegram API (`getMe`/`getUpdates`/
`sendMessage`) из этой песочницы не проверялась и не может быть проверена
— это нужно подтвердить на реальном сервере или с машины без такого
ограничения.
