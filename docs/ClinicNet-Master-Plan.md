# ClinicNet — Мастер-план для Claude Code
## Все фичи с нуля, по фазам

Это управляющий документ поверх `ClinicNet-Plan.md`. Он режет весь план на фазы, которые можно скармливать Claude Code последовательно — каждая фаза даёт рабочий результат и не блокирует остальные модули.

Логика порядка: сначала фундамент (без него ничего не масштабируется на сеть), потом клинический контур (расписание/ЭМК/направления — то, чем пользуются каждый день), потом деньги и склад, и только потом стационар/ИИ-слой/сетевые фишки — это уже надстройка над рабочей системой.

---

## Стартовый промпт (вставить в Claude Code первым сообщением)

```
Начинаем большой проект: расширение ClinicNet до enterprise-версии
для сетей клиник (несколько филиалов, разные врачи, стационар опционально).

Полный план лежит в файле ClinicNet-Plan.md (положу в /docs репозитория).
Мы будем идти по нему фазами, каждую фазу — отдельным заходом, с подтверждением
на каждом шаге. НЕ пытайся реализовать всё сразу.

Текущая фаза: ФАЗА 1 — Фундамент (Branch + RBAC v2 + мультифилиальное расписание).

Прежде чем писать любой код, изучи текущую структуру проекта:
- модели tenants/organizations (как сейчас устроена мультитенантность через django-tenants)
- модель User/Staff и текущий RBAC (какие права уже есть, как они хранятся — таблица,
  Enum, django-guardian, свой велосипед)
- модель Appointment/Schedule и как сейчас врач привязан к расписанию
- есть ли уже понятие "филиал"/"кабинет" в схеме, или всё плоское на уровне организации

Доложи, что нашёл, и предложи, как встроить модель Branch и RBAC v2
в существующую структуру с минимальными breaking changes. Жди моего
подтверждения перед тем как генерировать миграции.
```

## Фаза 1 — Фундамент

**Цель:** ввести филиал как сущность внутри тенанта, расширить RBAC до "роль × право × филиал".

Ключевые модели:
- `Branch` (название, адрес, часовой пояс, статус active/opening/closed)
- `StaffBranchAssignment` (врач/сотрудник ↔ филиал ↔ график работы: дни недели, часы)
- Расширение `Permission`/RBAC-таблицы полем `branch_scope`: `all | own_branch | specific_branches[]`
- Миграция существующих Appointment/Visit/Invoice — добавить `branch` FK (backfill на единственный текущий филиал по умолчанию, чтобы не сломать прод)

Результат фазы: врач может быть привязан к нескольким филиалам с разным расписанием, права проверяются с учётом филиала, расписание в UI фильтруется по филиалу без ручного переключения контекста (см. `multi-branch-schedule.html` — эталон UI).

**Файлы-ориентиры:** `network-dashboard.html`, `multi-branch-schedule.html` (визуальный эталон), раздел 1.10 и 3 в `ClinicNet-Plan.md`.

> **Статус в ClinicNet:** реализовано (см. `docs/PHASE1-DESIGN.md`) — с оговоркой, что репозиторий стартовал пустым, поэтому это не миграция существующих таблиц, а дизайн с нуля, сразу учитывающий Branch/RBAC v2.

## Фаза 2 — Клинический контур

**Цель:** то, чем пользуются каждый день: ЭМК на всю сеть, направления, базовая диагностика.

Модули:
- Единая ЭМК: снять текущие ограничения "карта = один филиал", если такие есть
- **Модуль "Направления" (Referral)** — уже есть отдельная детальная спецификация: `ClinicNet-Referrals-Prompt.md`. Использовать её как под-промпт внутри этой фазы.
- Лаборатория/диагностика (базовая версия): заказ анализа из карты, ручной ввод результата (без интеграции с анализаторами на первом этапе — это отдельная фаза 5/6 при необходимости)
- Медицинские шкалы/индексы — расширение того, что уже есть для стоматологии, на общемедицинские кейсы (если клиника не только стоматология)

Результат фазы: врач видит полную историю пациента по всей сети, может направить пациента к коллеге (в своём или другом филиале) прямо из приёма.

> **Статус в ClinicNet:** в работе (см. `docs/PHASE2-REFERRALS-DESIGN.md`).

---

## Фаза 3 — Финансы и склад

**Цель:** деньги должны сходиться на уровне сети, а не только филиала.

Модули:
- Мультикасса: каждая касса привязана к филиалу, но есть консолидированный отчёт по сети
- Единый прайс с возможностью филиал-специфичных цен/скидок (переопределение, не дублирование прайса)
- Страхование/ДМС-логика: лимиты по полису, разделение чека пациент/страховая
- Складской учёт по филиалам: списание по факту приёма, минимальные остатки, авто-заказ поставщику (это же источник алерта "остаток анестетика < 3 дней" на дашборде сети)

**Зависит от:** Фазы 1 (Branch), опционально пересекается с Фазой 2 (списание материалов при закрытии Visit).

---

## Фаза 4 — Стационар (опционально)

Реализовать **только если** продукт реально целится в мини-стационары, а не только амбулаторные клиники — иначе это мёртвый вес в кодовой базе. Решить это явно перед стартом фазы, а не по умолчанию.

Модули: коечный фонд, госпитализация/выписка/перевод, врачебные назначения, операционный модуль.

---

## Фаза 5 — AI-слой

**Цель:** фичи-дифференциаторы, которые реально выделяют продукт на рынке (раздел 2 плана).

Рекомендуемый порядок внутри фазы (от простого к сложному):
1. Предиктивная аналитика оттока пациентов (модель на истории визитов — можно начать с простой эвристики "не был > X месяцев при обычной периодичности визитов", ML — уже вторая итерация)
2. AI-триаж через WhatsApp/Telegram-бота (подбор специальности + предложение слота)
3. Голосовой ввод в ЭМК (voice-to-structured-data) + проверка на лекарственные взаимодействия
4. Умный балансировщик загрузки по сети (предложение альтернативного филиала при перегрузке)

**Архитектурная заметка:** вынести в отдельный сервис (FastAPI) поверх read-replica Postgres, не грузить транзакционную БД инференсом — см. раздел 3 плана.

---

## Фаза 6 — Сетевые фичи

Программа лояльности на всю сеть, маркетплейс направлений между клиниками-партнёрами, симулятор загрузки нового филиала, what-if планирование расписания. Это управленческая надстройка — имеет смысл только когда сеть реально из нескольких филиалов в проде, не раньше.

---

## Как использовать этот документ с Claude Code

1. Положить `ClinicNet-Plan.md`, `ClinicNet-Referrals-Prompt.md` и этот файл в `/docs` репозитория.
2. Вставить стартовый промпт (см. выше) — начнёте с Фазы 1.
3. После того как Фаза 1 реально в проде (не просто "код написан", а прошла ревью и деплой) — новый заход в Claude Code со ссылкой на этот файл и словами "переходим к Фазе 2".
4. Не начинать следующую фазу, пока предыдущая не стабилизировалась — это как раз то, от чего явно предостерегает раздел "не переходи к следующему шагу без подтверждения" в промпте для Referral-модуля.
