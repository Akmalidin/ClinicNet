# Промпт для Claude Code — старт Фазы 2 (ClinicNet)

Отдельный, самостоятельный проект **ClinicNet** — новый репозиторий, новая структура с нуля. Не путать с dental/SADAF/ODONTIS — это другая кодовая база, ничего не наследуется.

Предполагается, что Фаза 1 (Branch + RBAC v2 + мультифилиальное расписание) уже смёржена в main и задеплоена (не просто на ветке) — см. предыдущий чек-лист ручной проверки.

## Стартовый промпт

```
Проект: ClinicNet — отдельная новая система для сетей клиник/больниц.
Фаза 1 (Branch + RBAC v2 + мультифилиальное расписание) уже в main и задеплоена.

Переходим к ФАЗЕ 2 по плану ClinicNet-Master-Plan.md — клинический контур:
единая ЭМК на всю сеть + модуль направлений + базовая диагностика.

Полная спецификация модуля направлений — ClinicNet-Referrals-Prompt.md,
используй её как основной документ для этой части фазы.

Прежде чем писать код:

1. Изучи фактическую структуру проекта ClinicNet после Фазы 1 (это новый
   репозиторий, ничего не унаследовано из других проектов) — модели Branch,
   StaffBranchAssignment, Appointment, RBAC-таблицу, related_name на всех
   FK. Не предполагай ничего по памяти о других проектах — бери только то,
   что реально в этом кодовом дереве.

2. Проверь, как сейчас устроена карта пациента (ЭМК) — есть ли уже
   фильтрация по филиалу на уровне карты (могла появиться нечаянно, если
   Visit получил branch и где-то есть неявный branch-scoped queryset на

   сеть, филиал должен фильтровать только Visit/Appointment внутри неё,
   а не саму карту пациента.

3. Сверь модель Referral из ClinicNet-Referrals-Prompt.md с реальными
   моделями Patient/Visit/Appointment/Branch/Staff, которые сложились
   после Фазы 1 в этом репозитории — имена полей и related_name могли
   отличаться от того, что предполагалось при написании спецификации.
   Доложи расхождения до генерации миграций.

4. Проверь, есть ли уже сервис отправки WhatsApp/Telegram-уведомлений —
   если Фаза 1 его не создавала, для Фазы 2 нужно будет создать с нуля
   (в отличие от проектов, где такой сервис мог уже существовать).

5. Проверь, используется ли django-fsm где-то в проекте для статусов
   (например, у Appointment) — если да, привести Referral.status
   к тому же паттерну для консистентности.

После разведки — доложи находки и предложи план по пунктам:
   a) Единая ЭМК (что нужно построить — в новом проекте, скорее всего,
      с нуля, а не "поправить")
   b) Модуль направлений — по шагам 1-9 из раздела "Последовательность
      реализации" в ClinicNet-Referrals-Prompt.md
   c) Базовая диагностика: заказ анализа из карты + ручной ввод результата
      (без интеграции с лабораторными анализаторами — отдельная фаза)

Жди моего подтверждения после разведки, прежде чем генерировать миграции.
Идём по шагам, не всё разом.
```

## Ручная проверка после этой фазы (без тестов, тот же формат, что и Фаза 1)

- Карта пациента с визитами в двух разных филиалах — видна вся история, а не только текущий филиал
- Направление внутри одного филиала и кросс-филиальное — оба целиком, до появления записи в расписании принимающего врача
- Отклонение направления — `outcome_note` обязателен, уведомление уходит направившему врачу
- Очередь направлений на дашборде — фильтры по филиалу и по сети целиком
- Регрессия: обычный однофилиальный сценарий (как в Фазе 1) по-прежнему работает без лишнего трения
